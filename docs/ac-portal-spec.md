## 2. 작업 원칙 (모든 화면에 공통 적용)

1. **화면에는 고를 것만 둔다.** 모델 선택, 프롬프트 작성, 온도·토큰 설정은 이용자 화면에 두지 않는다. 그런 설정은 관리자 화면에서만 다룬다.
2. **일정한 점검은 버튼으로, 그때그때 필요한 요청은 채팅으로 한다.** 매번 같은 기준으로 하는 점검은 관리자가 버튼으로 등록하고, 이용자는 누르기만 한다. 그 밖의 추가 점검이나 수정 요청은 채팅으로 받는다.
3. **AI가 지적하거나 고친 내용은 모두 문서 위 위치와 함께 보여 준다.** "어디가, 왜, 어떻게 고치면 되는지"를 한 묶음으로 보여 주고, 반영 여부는 이용자가 정한다.
4. **바뀐 내용은 언제든 되돌릴 수 있다.** AI가 고친 것이든 이용자가 고친 것이든 모두 버전으로 남기고, 이전 버전과 비교하거나 되돌릴 수 있다.
5. **숫자 계산은 프로그램이 한다.** AI는 "어느 숫자끼리 맞아야 하는지"만 찾는다. 합계, 비율, 날짜·요일 같은 계산은 서버의 계산 코드가 맡는다.
6. **지침은 한곳에서 관리한다.** 기능마다 쓰는 지침(스킬 또는 지침 프롬프트)과 점검 항목은 관리자 화면 한곳에서 고치고, 고친 내용은 모든 이용자에게 바로 적용된다.
7. **한 곳을 고치면 영향을 받는 곳을 함께 보여 준다.** 과제의 숫자나 자료를 고치면 같은 사실을 쓰는 다른 자료와 평가자가이드의 해당 부분을 표시한다.
8. **양식과 파일 구조는 고정하지 않는다.** 보고서 양식, 과제 파일의 방향(가로·세로), 쪽 크기, 자료 개수, 자료 표기 방식은 용역마다 다르다. 특정 파일에 맞춘 규칙을 만들지 않는다. AI가 파일을 먼저 읽고 구조를 제안하며, 이용자는 확인만 한다. 확인한 구조는 용역별로 저장해서 다시 쓴다.

### 2-1. 처음 쓰는 사람을 위한 화면 원칙

| 번호 | 원칙 | 화면에 적용하는 방법 |
|---|---|---|
| 1 | 첫 화면에서 전체 순서를 보여 준다. | 시작 화면(6-0)에 5단계를 "넣는 것 → 나오는 것"으로 한 줄씩 보여 준다. 가지고 있는 파일에 따라 어느 단계부터든 시작할 수 있다. |
| 2 | 단계마다 같은 틀을 쓴다. | 위: 화면 제목 + "무엇을 결정하는지" 한 줄 ("이 단계에서 할 일" 안내는 접혀 있고 누르면 펼쳐짐) → 가운데: 결정할 것 → 아래: [이전 단계] 버튼, 그 단계를 마친 뒤에만 [다음 단계] 버튼 |
| 3 | 지금 어디에 있는지 항상 보인다. | 단계 표시줄에 단계마다 "완료 / 진행 중 / 시작 전"을 글자로 적는다. |
| 4 | 한 화면에서 가장 중요한 버튼은 1개만 파란색으로 둔다. | 나머지 버튼은 테두리 버튼으로 둔다. 아래쪽 [다음 단계], 사용법 안내 닫기, 채팅 [보내기]도 테두리 버튼이다. 결과 카드의 [반영]은 펼친 카드에서만 파란색이다. |
| 5 | 누를 수 없는 버튼은 이유를 바로 옆에 적는다. | 예: "파일 3개 중 2개를 올렸습니다. 참조할 평가자가이드를 올려 주세요." |
| 6 | 빈 화면에는 할 일과 버튼을 둔다. | 예: 점검 결과가 없으면 "아직 점검하지 않았습니다" + [전체 점검] 버튼 |
| 7 | 오래 걸리는 작업은 진행 단계와 예상 시간을 보여 준다. | 예: "1. 음성을 글로 바꾸기 → 2. 화자 나누기 (1시간 녹음 기준 약 5분)" |
| 8 | 아이콘은 그림 문자(이모지) 대신 선 아이콘을 쓰고, 항상 글자와 함께 쓴다. 색만으로 뜻을 전하지 않는다. | 점검 항목은 색 + 이름, 상태는 아이콘 + 글자 |
| 9 | 글자와 누르는 곳을 충분히 크게 한다. | 본문 15px 이상, 보조 글 13px 이상, 버튼 높이 36px 이상(휴대폰 44px 이상) |
| 10 | 키보드로도 쓸 수 있다. | 모든 버튼에 Tab으로 이동, 포커스 테두리 표시, Esc로 작은 메뉴 닫기. 화면을 다시 그려도 포커스를 그 자리에 두고, 화면이 바뀌면 제목으로 옮긴다. 진행 상황은 화면 읽기 프로그램에 알린다. 드래그 대신 [이 항목 고쳐 달라고 하기]를 쓸 수 있다. 오른쪽 칸 탭은 화살표 키로 옮긴다. |
| 11 | 되돌릴 수 없는 동작만 한 번 더 묻는다. | 점검 항목 지우기 등은 "정말 지울까요?"를 묻는다. 반영·고치기처럼 되돌릴 수 있는 동작은 묻지 않고 수정 기록에서 되돌리게 한다. |
| 12 | 편집 화면을 처음 열면 사용법 3가지를 보여 준다. | 목차에서 항목 고르기 / 글자 드래그로 그 부분만 고치기 / 점검 버튼 → 오른쪽 결과. 닫으면 다시 뜨지 않는다. |
| 13 | 이용자에게 필요 없는 선택지는 보이지 않는다. | 관리자 화면 버튼은 관리자 계정에만 보인다. |
| 14 | 주소만으로 원하는 화면을 열 수 있다. | 단계와 관리자 메뉴가 주소에 남는다(예: `#step-3`, `#admin-checks`). 동료에게 주소를 보내면 같은 화면이 열린다. |
| 15 | 저장되지 않은 수정이 있으면 창을 닫기 전에 묻는다. | 실제 서비스에서는 자동 저장하고, 저장 전이면 브라우저 확인 창을 띄운다. |
| 18 | 실패하면 그 자리에서 알리고 다시 할 길을 준다. | 무엇이 실패했는지, 짐작되는 이유, [다시 시도] / [이전으로]를 진행 화면 자리에 보여 준다. 이미 한 작업은 지우지 않는다. |
| 17 | 이용자 화면에는 결정에 필요한 것만 둔다. | 스킬·지침이 바뀌면 함께 바뀌는 세부 내용(근거 표시, 스킬 이름, 용역 설정 저장 안내, 구조 분석 표, 후보의 세부 평가 항목)은 관리자 화면으로 옮기거나 접힌 "자세히 보기" 안에 둔다. 2-4 참고 |
| 16 | AI가 만든 결과가 나오는 곳에는 AI 수정 요청 상자를 같은 모양으로 둔다. | 결과 바로 아래에 [AI에게 고쳐 달라고 하기] 버튼 하나만 두고, 누르면 [예시 요청 2개 + 입력창]이 펼쳐진다. AI는 바로 고치지 않고 **바뀌는 부분(지운 글자·넣은 글자)을 먼저 보여 주고**, 이용자가 **[반영] / [다른 안 제안받기] / [반영 안 함]** 가운데 하나를 고른다. 반영한 뒤에도 [되돌리기]를 할 수 있다. 점검 결과 카드와 전체 수정 제안도 같은 세 가지 선택지를 쓴다. |

### 2-2. 화면 용어

명세에서 쓰는 말과 화면에 보이는 말을 나눈다. 화면에는 오른쪽 말만 쓴다.

| 명세 용어 | 화면 표시 |
|---|---|
| 블록 | 항목 |
| 블록 목록 | 목차 |
| 묶음 | 구분 |
| 수정 범위 | 고칠 범위 |
| 버전 기록 | 수정 기록 |
| 구조 확인 화면 | 목차 확인 |
| 점검 항목 | 점검 항목 (관리자), 점검 버튼 (이용자) |
| isomorph-ac 확인 단계 A1 / A2 / B1 | 예전 과제 풀이 다시 보기 / 새 과제 풀이 짜기 / 자료 나누기 (단계 기호는 관리자 화면에만) |
| RAG로 찾은 부분 | 찾은 부분 |
| Speaker 1 | 화자 1 |
| 미선정 제안안 | 채택되지 않은 제안 주제 |
| [무시] | [반영 안 함] |
| 판별 지점 (isomorph-ac 용어) | 핵심 판단 지점 — 상위·하위 응시자의 수행이 갈리는 곳. 스킬 본문의 말은 바꾸지 않고 화면에서만 바꿔 보여 준다. |

### 2-3. AI 수정 요청 구간

| 화면 | 고칠 대상 | 요청 예시 |
|---|---|---|
| ① 평가 조건 확인 | 해결과제 수, 측정 역량, 업무 관련성 등 | 해결과제를 3개로 늘려 줘 |
| ① 해결과제 후보 | 후보 5개 | 환경 분야는 빼고 다시 만들어 줘 |
| ① 스토리맵 | 스토리맵 내용 | 역할 간 갈등을 더 분명하게 해 줘 / 평가대상자를 3명으로 늘려 줘 |
| ② 확인 지점(3-6) | 그 지점의 결과(풀이 복원, 풀이 설계, 과제 분석) | 핵심 판단 지점을 하나 더 넣어 줘 / 난이도를 한 단계 낮춰 줘 |
| ②④⑤ 편집 화면 | 고를 항목 또는 드래그한 글자 (채팅) | 이 자료를 더 짧게 줄여 줘 |
| ②④⑤ 편집 화면 | 과제 전체 ([전체 수정 제안]) | 버튼만 누르면 AI가 과제 전체를 읽고 고칠 곳 여러 개를 한꺼번에 제안 |
| 목차 확인 | 항목 나누기·구분 | 자료 3을 장별로 두 항목으로 나눠 줘 |
| ③ 녹취록 확인 | 화자 지정, 발언 글자 | 00:13:30 발언은 화자 1의 발언이야 / "총예산"을 "총 예산"으로 모두 고쳐 줘 |
| ③ 양식 칸 확인 | 칸별 채우는 방법 | 향후일정은 직접 입력으로 바꿔 줘 / 위치 행에 쪽 번호는 빼 줘 |
| ③ 미리보기 | 보고서 문장 | 반영 방향 문장을 더 짧게 줄여 줘 / 검토위원 의견 앞에 위원 이름을 붙여 줘 |
| ④ 수정 요청 목록 | 요청 나누기·합치기·고르기 | 마지막 요청을 둘로 나눠 줘 / 발주처 의견이 있는 요청만 남겨 줘 |
| 관리자: 지침 관리 | SKILL.md, references/ 문서, 직접 쓴 지침 | 후보를 5개에서 3개로 줄여 줘 |
| 관리자: 점검 항목 관리 | 점검 항목의 지침 | 기준을 더 구체적으로 써 줘 |

- 앞 단계 결과를 고치면 그 결과를 쓰는 다음 단계에도 반영한다. 예: ③ 보고서 문장을 고치면 ④ 수정 요청 목록에도 같은 내용이 들어간다.

## 3. 지침 관리 방식: 스킬 불러오기 + 지침 프롬프트

### 3-1. 기본 방식: 기존 스킬을 그대로 불러온다

기존 스킬 폴더(`SKILL.md` + `references/` + `scripts/`)를 관리자가 zip으로 올리면 포털이 다음처럼 나눠 쓴다.

| 스킬 구성 | 포털에서 쓰는 방법 |
|---|---|
| `SKILL.md` 본문 | 해당 기능의 지침 프롬프트(시스템 프롬프트)로 넣는다. |
| `references/` 문서 | 자료·DB 관리의 참고 문서에 넣고, 지침이 그 문서를 언급할 때 찾아서 함께 넣는다. |
| `examples/` 문서 | 작성 예시로 쓰고, 3-4의 시험 실행에서 예시 입력으로도 쓴다. |
| `scripts/` 코드 | 서버의 격리된 실행 환경에서 돌린다. 예: pptx 읽기·쓰기, 표 계산 |
| `SKILL.md` 머리말(name, description) | 기능 선택 화면의 이름과 설명으로 쓴다. |

**미리 알아 둘 제약**
- 기존 스킬은 Claude가 웹 검색, 파일 생성, 코드 실행 도구를 쓴다고 가정하고 쓰여 있다. 오픈소스 모델에서 같은 결과를 내려면 포털이 같은 도구(웹 검색, 파일 읽기·쓰기, 코드 실행)를 모델에 제공해야 하고, 모델은 도구 호출(function calling)을 지원해야 한다.
- 도구를 제공하지 못하는 단계는 아래 3-2 방식으로 대신한다.

### 3-2. 대체 방식: 지침 프롬프트를 관리자가 직접 쓴다

스킬을 그대로 돌리기 어려운 기능, 또는 해당 스킬이 없는 기능은 관리자가 지침 프롬프트를 직접 입력한다.

### 3-3. 스킬 파일 보기와 고치기 (관리자 화면: 지침 관리)

| 기능 | 내용 |
|---|---|
| 파일 보기 | 왼쪽에 스킬 폴더의 파일 목록(SKILL.md, references/, scripts/, examples/)을 두고, 누르면 내용을 보여 준다. |
| 직접 고치기 | SKILL.md, references/, examples/ 문서는 화면에서 바로 고친다. scripts/ 코드는 보기만 하고, 고치는 것은 개발 담당 권한으로 둔다(잘못 고치면 기능이 멈추므로). |
| AI에게 고쳐 달라고 하기 | 파일 아래의 AI 수정 요청 상자(원칙 16)에 적는다. AI는 3-5 규칙을 지켜 고친 안을 만들고, 바뀌는 부분과 규칙 점검 결과를 함께 보여 준다. |
| 저장 전 규칙 점검 | 저장 버튼을 누르면 3-5의 자동 점검을 돌린다. 통과하지 못한 항목이 있으면 이유를 보여 주고, 그래도 저장할지 묻는다. |
| 시험 실행 | 예시 파일(examples/ 또는 관리자가 고른 파일)로 **이전 버전과 새 버전의 결과를 나란히** 보여 준다. |
| 버전 | 저장할 때마다 버전이 남는다(고친 사람, 날짜, 바꾼 이유, 바뀐 줄). 이전 버전으로 되돌릴 수 있다. |
| 제안 대기 | 다른 화면에서 들어온 스킬 수정 제안(예: ④의 검토 교훈)을 모아 보여 준다. 관리자가 [반영] / [반영 안 함]을 고른다. |

### 3-4. 기능별 지침 연결

| 기능 | 연결할 지침 | 방식 |
|---|---|---|
| ① 주제 탐색 | `ac-topic-storymap` | 스킬 불러오기 |
| ② 과제 초안(평가과제 + 평가자가이드) | `isomorph-ac` | 스킬 불러오기 |
| ③ 검토회의 보고서 | (스킬 없음) 녹취록 요약·양식 칸 채우기 지침 | 지침 프롬프트 직접 쓰기 |
| ④ 검토의견 반영 | (스킬 없음) 수정 요청 반영 지침. 필요하면 `isomorph-ac` 일부를 참조한다. | 지침 프롬프트 직접 쓰기 |
| ⑤ 검수 | 점검 항목(4장)을 그대로 사용 | 점검 버튼 |

### 3-5. AI가 스킬을 고칠 때 지킬 규칙 (skill-creator 기준)

| 규칙 | 이유 | 자동 점검 |
|---|---|---|
| 머리말의 `name`은 바꾸지 않는다. | 이름이 바뀌면 기능과 스킬의 연결이 끊긴다. | 이름이 그대로인지 |
| `description`에는 "무엇을 하는지"와 "언제 쓰는지"를 함께 적는다. | 모델은 description을 보고 스킬을 쓸지 정한다. | description이 비어 있지 않은지 |
| SKILL.md 본문은 500줄 이하로 둔다. 길어지면 references/ 문서로 옮기고 SKILL.md에 "언제 읽을지"를 적는다. | 본문은 매번 통째로 읽히므로 짧을수록 정확하고 빠르다. | 줄 수 |
| 300줄이 넘는 references/ 문서에는 첫머리에 목차를 둔다. | 필요한 부분만 찾아 읽게 하기 위해 | 줄 수와 목차 |
| SKILL.md에 적은 references/·scripts/ 경로는 실제로 있어야 한다. | 없는 파일을 가리키면 그 단계가 실패한다. | 경로가 파일 목록에 있는지 |
| "반드시", "절대" 같은 강한 말 대신 이유를 함께 적는다. | 이유를 알면 모델이 처음 보는 경우에도 맞게 판단한다. | 강한 말이 새로 늘었는지(경고만) |
| 특정 과제 하나에만 맞는 규칙을 넣지 않고, 다른 과제에도 쓸 수 있게 쓴다. | 스킬은 여러 용역에 반복해서 쓰인다. | 없음 (사람이 확인) |
| 고친 뒤에는 예시 파일로 이전 버전과 결과를 비교한다. | 고친 것이 실제로 더 나은지 확인하기 위해 | 시험 실행 |

### 3-6. 스킬의 확인 지점 (★정지)

- 스킬 본문에 "★정지"로 표시된 단계는 AI가 작업을 멈추고 이용자의 확인을 받는 지점이다(예: isomorph-ac의 참조 풀이 복원, 신규 풀이 설계, 참조 과제 분석).
- 포털은 SKILL.md에서 ★정지 표시를 찾아 화면의 **확인 단계**로 보여 준다. 단계마다 결과 요약 + AI 수정 요청 상자 + [확인하고 다음으로] 버튼을 둔다.
- 관리자가 SKILL.md에서 ★정지를 넣거나 빼면 이용자 화면의 확인 단계도 그대로 바뀐다.

## 4. 점검 항목 관리 (현실적합성, 오탈자 등)

### 4-1. 구조

관리자가 점검 항목을 등록하면, 이용자의 편집 화면 위쪽에 버튼으로 나타난다.

| 등록 칸 | 설명 | 예시 |
|---|---|---|
| 이름 | 버튼에 보일 이름 | 현실적합성 점검 |
| 지침 프롬프트 | 무엇을 어떤 기준으로 찾을지 적는다. | 실제 있는 법령·제도인가, 그 직급에 그 권한이 있는가, 예산·인원 규모가 현실적인가, 날짜와 요일이 맞는가 |
| 계산 코드 사용 | 숫자 계산이 필요한 항목이면 켠다. | 수치 점검에서 켬 |
| 표시 색 | 문서 위에 표시할 색 | 주황 |
| 보이는 기능 | 어느 단계 화면에 버튼을 보일지 정한다. | ②, ④, ⑤ |
| 순서·사용 여부 | 버튼 순서, 숨김 여부 | |

### 4-2. 처음에 넣어 둘 점검 항목 (관리자가 고치거나 지울 수 있음)

| 이름 | 찾는 것 | 계산 코드 |
|---|---|---|
| 현실적합성 | 실제와 맞지 않는 제도·권한·규모·일정 | 날짜·요일만 사용 |
| 오탈자 | 맞춤법, 띄어쓰기, 오타, 기관명·인물명 표기 불일치 | 사용 안 함 |
| 수치 계산 | 예산 합계, 비율, 증감률, 인원 합계가 맞는지. 표와 차트 안의 숫자도 포함한다. | 사용 |
| 자료 간 일치 | 같은 사실(금액, 날짜, 인물, 직위)이 자료마다 다르게 적혔는지, 자료끼리 조건이 충돌하는지 | 사용 |
| 근거 없는 내용 | 다른 자료에 근거가 없는 주장이나 결론 | 사용 안 함 |
| 표현 | 뜻이 모호한 용어, 응시자에게 정답을 알려 주는 표현, 차별적 표현 | 사용 안 함 |
| 구성 점검 | 자료 번호가 빠지거나 겹치는지, 표지의 "총 n장" 안내와 실제 장수가 맞는지, 쪽 번호가 이어지는지 | 사용 |
| 과제-가이드 일치 | 가이드가 정답 근거로 든 자료·수치가 과제에 실제로 있는지, 과제의 숫자와 가이드의 계산 답이 맞는지 | 사용 |

### 4-3. 점검 결과를 보여 주는 방식

- 문서 위 해당 글자에 점검 항목 색으로 밑줄을 긋는다.
- 오른쪽에 결과 카드를 띄운다. 카드는 **점검 항목 · 위치(예: 자료3, 2번째 표) · 이유** 한 줄로 접혀 있고, 누르면 **바뀐 부분(지운 글자·넣은 글자)**, [직접 다듬기], 버튼이 펼쳐진다. 한 번에 한 장만 펼쳐진다.
- 결과가 여러 개면 [하나씩 검토]로 5-6 검토 모드를 연다.
- 선택지는 [반영] / [다른 안 제안받기] / [반영 안 함] 세 가지다. [반영]을 누르면 고친 안이 문서에 들어가고 새 버전이 남는다. [다른 안 제안받기]를 누르면 AI가 같은 문제에 대해 다른 고친 안을 낸다.
- 추가 점검이나 다른 수정은 채팅으로 요청한다. 예: "자료 2와 자료 5의 예산이 왜 다른지 다시 봐 줘"

## 5. 공통 편집 화면 (②, ④, ⑤가 같이 씀)

### 5-1. 배치

```
┌──────────────┬──────────────────────────────┬────────────────────┐
│ 목차          │ 점검: [현실적합성] [오탈자] …   │ 채팅 / 점검 결과 /  │
│ 평가과제      │        [바뀐 부분 보기] [받기]   │ 수정 기록           │
│               │                              │ 고칠 범위: 자료 2   │
│  구조         │                              │ ─────────────────  │
│  공통 자료    │  (선택한 블록 내용)            │ 결과 카드 …         │
│  역할별 자료  │                              │                    │
│ 평가자가이드  │  [바뀐 부분 보기]              │ [고칠 내용 입력]    │
└──────────────┴──────────────────────────────┴────────────────────┘
```

- 점검 버튼 줄(위)과 보기·받기 버튼(오른쪽 끝)을 나눠 둔다.
- 처음 열면 사용법 3가지를 본문 위에 보여 준다(2-1의 12번).
- 문서 위에는 [전체 점검]과 [전체 수정 제안]만 보이고, 항목별 점검 버튼은 "항목 골라 점검"을 눌러야 펼쳐진다.
- 휴대폰 폭에서는 세 영역을 탭(목차 / 문서 / 채팅·결과)으로 바꿔 보여 준다.

### 5-2. 수정 방법 3가지

| 방법 | 동작 | 채팅에 걸리는 범위 |
|---|---|---|
| 블록 클릭 | 왼쪽 목록에서 "자료 2"를 누른다. | 채팅창 위에 "수정 범위: 자료 2"가 표시되고, 요청은 자료 2에만 적용된다. |
| 드래그 선택 | 본문에서 글자를 드래그하면 작은 메뉴가 뜬다: [AI에게 고쳐 달라고 하기] [직접 고치기] | 드래그한 글자에만 적용된다. |
| 전체 요청 | 범위를 지정하지 않고 채팅에 쓴다. | 문서 전체. AI가 어느 블록을 고쳤는지 함께 알려 준다. |
| 전체 수정 제안 | [전체 수정 제안] 버튼을 누른다. | 평가과제와 평가자가이드 전체. AI가 고칠 곳을 여러 개 찾아 점검 결과 탭에 카드로 올린다. 카드마다 [반영] / [다른 안 제안받기] / [반영 안 함]을 고르고, [모두 반영] / [모두 반영 안 함]도 쓸 수 있다. |

### 5-3. 바뀐 부분 확인

- **바뀐 부분 보기**를 켜면 이전 버전과 비교해 지운 글자는 빨간 취소선, 넣은 글자는 초록 바탕으로 보인다.
- 왼쪽 블록 목록에서 바뀐 블록 옆에 점을 찍는다.
- **버전 기록**에는 버전마다 "누가(이용자/AI), 무엇 때문에(채팅 요청 문장, 점검 항목 이름), 어느 블록을" 고쳤는지 한 줄로 남는다. 아무 버전이나 골라 되돌릴 수 있다.
- 고친 블록과 같은 사실을 쓰는 다른 블록(평가자가이드 포함)에는 "함께 확인 필요" 표시를 붙인다(작업 원칙 7).

### 5-4. pptx를 블록으로 나누는 규칙

과제 파일은 용역마다 가로·세로 방향, 쪽 크기, 자료 개수, 자료 제목을 적는 방식이 다르다. 그래서 고정된 규칙 대신 아래 순서로 나눈다.

**1) AI가 구조를 제안할 때 쓰는 단서**

| 단서 | 쓰는 방법 |
|---|---|
| 자료 표기 | 모든 글상자(그룹 도형 안 포함)에서 자료 번호 표기를 찾는다. "자료 3.", "자료3", "[자료 3]", "<자료 3>", "참고자료", "붙임" 등 여러 표기를 받는다. 제목 칸에 없을 수 있으므로 제목 칸만 보지 않는다. |
| 여러 장 표시 | "(1/4)", "1/4", "계속" 같은 표시가 붙은 연속 슬라이드는 한 자료로 묶는다. |
| 간지 슬라이드 | 글상자 하나만 있고 "역할별 자료", "평가대상자 A", "○○과 ○○○ 과장" 같은 글이 있는 슬라이드는 묶음의 시작으로 본다. 간지가 없으면 모두 "공통 자료"로 둔다. |
| 자료 번호가 없는 슬라이드 | 표지, 안내, 상황개요, 가상조직, 마침 등은 "구조" 묶음에 둔다. |
| 쪽 번호 | 슬라이드 안의 인쇄 쪽 번호("- 6 -", "6", "6/20" 등)를 찾아 위치 표기에 쓴다. 쪽 번호가 없으면 슬라이드 순번을 쓴다. |
| 방향·크기 | 가로·세로, 쪽 크기는 블록 나누기에 쓰지 않고 파일 정보로만 기록한다. 내보낼 때 그대로 지킨다. |
| 차트·그림 | 차트 안의 숫자는 읽어서 수치 점검에 쓴다. 차트와 그림은 AI가 고치지 않고 "직접 고쳐야 할 곳"으로 표시한다. |

**2) 이용자 확인 (화면 이름: 목차 확인)**
- 파일을 처음 열면 AI가 제안한 블록 목록을 보여 준다. 블록마다 이름, 슬라이드 범위, 쪽, 묶음이 표로 나온다.
- 이용자는 틀린 곳만 고친다. 묶음 바꾸기, 앞 블록과 합치기, 블록 나누기를 할 수 있다.
- 확인한 구조와 자료 표기 방식은 용역별로 저장되어, 같은 용역의 다음 파일을 열 때 먼저 적용된다.

**확인용 예시 (받은 샘플 집단토론 과제, 세로형 20장)**: 제목이 제목 칸이 아니라 글상자에 있었고, "자료 3"이 4장에 걸쳐 있었으며, 역할별 간지가 3장 있었다. 위 단서로 "구조 / 공통 자료 / 평가대상자 A·B·C" 묶음으로 나눌 수 있음을 확인했다.

### 5-5. 파일 형식

- ②에서 만든 평가과제는 pptx, 평가자가이드는 pptx 또는 docx(참조 가이드와 같은 형식)로 내보낸다. 평가과제의 방향(가로·세로), 쪽 크기, 레이아웃, 글꼴은 참조 평가과제를 따른다.
- ④와 ⑤는 pptx를 불러와 5-4 순서(AI 제안 → 이용자 확인)로 나눈 뒤 같은 편집 화면에 보여 준다.
- pptx를 고칠 때는 글자만 바꾸고 레이아웃, 글꼴, 표 모양은 그대로 둔다.

### 5-6. AI 제안 검토 모드

AI 제안이 여러 개일 때(전체 수정 제안, 점검 결과, 검토의견 반영) 오른쪽 좁은 칸에 쌓아 두지 않고, 문서 위에서 하나씩 넘기며 정한다. 검토회의 뒤 의견을 하나씩 반영하는 실제 업무 순서와 같다.

| 구성 | 내용 |
|---|---|
| 위쪽 띠 | "제안 2 / 4 · 상황개요" 진행 표시, [검토 끝내기] |
| 문서 | 해당 항목이 열리고, 바뀌는 자리에 지운 글자·넣은 글자가 문서 안에 그대로 표시된다. |
| 이유 | 제안 이유 한두 줄, 영향받는 다른 항목 수("평가자가이드 1곳도 함께 확인 필요") |
| 버튼 | [반영] (파란색) / [다른 안 제안받기] / [넘기기]. 키보드: Enter 반영, → 넘기기 |
| 끝 | "4건 가운데 3건 반영, 1건 넘김" 요약과 [반영한 것 모두 되돌리기]. 넘긴 제안은 점검 결과에 남는다. |

## 6. 기능별 화면

### 6-0. 시작 화면

| 구분 | 내용 |
|---|---|
| 보여 주는 것 | 진행 중인 과제 목록(과제 이름, 현재 단계, 마지막 수정일), [새 과제 시작] 버튼, 5단계 순서 카드 |
| 순서 카드 | 단계마다 이름, 넣는 것, 나오는 것, [이 단계부터 시작] 버튼. 예: 스토리맵이 이미 있으면 ② 과제 초안부터 시작한다. |

### ① 주제 탐색 (ac-topic-storymap 스킬의 진행 절차를 따름)

스킬은 "각 단계 끝에서 사용자 확인을 받고 넘어간다"고 정한다. 한꺼번에 완성본을 내면 부분 수정이 반복되기 때문이다. 화면도 같은 순서로 나눈다.

| 화면 단계 | 스킬 단계 | 보여 주는 것 | 이용자가 확인할 것 |
|---|---|---|---|
| 1. 조건 입력 | — | 발주처, 직급, 평가 기법 (모두 필수). 발주처·직급은 자료·DB(7-1)에 있는 값으로 만든 드롭다운이며, 직급 목록은 고른 발주처에 맞춰 바뀐다. | 세 항목 입력 |
| 2. 평가 조건 확인 | 0·1단계 | 해결과제 개수, 해결과제별 측정 역량, 업무 관련성(유관/무관), 가상조직 기관 유형, 해결과제 간 소재 연결 방식, 역량 정의 출처, 이번에 조회한 중복 배제 자료(파일명). 항목마다 근거 표시 [DB 확인] / [설정 문서] / [추론] / [확인 불가]를 붙인다. | 조건이 맞는지. 스킬이 사용자에게 묻도록 정한 질문(예: 주제풀에서 채택되지 않은 제안 주제도 배제할지)에 답해야 다음으로 넘어간다. |
| 3. 기출 구조 분석 확인 | 2단계 | 관찰한 특징, 과제 단위·딜레마 구조·규모·업무 범위 표, 추가 관찰 특징. 근거 기출 파일명 | 분석이 맞는지. 확인하면 용역 설정 문서에 저장한다. 용역 설정 문서의 DB 기준 정보가 지금과 같으면 이 단계는 저장된 결과를 보여 주고 바로 넘어간다. |
| 4. 해결과제 1 후보 고정 | 3단계 | 서로 다른 분야의 후보 5개. "기출과 겹칠 수 있는 후보"는 아래쪽 접힌 묶음에 두고, 고정하려 하면 가까운 기출과 함께 한 번 더 묻는다. 후보마다 가상조직, **해결과제명, 측정 역량**, 내용, 역량 측정 연관성, 구조 대조, 소재 판정(가장 가까운 기출과 근거 파일), 점검표 결과 | 후보 하나를 고정하거나, 고쳐서 고정한다. |
| 5. 해결과제 2…n 후보 고정 | 4단계 | 고정한 가상조직이 맡을 만한 다른 업무로 후보 5개. 해결과제 수만큼 반복 | 해결과제마다 하나씩 고정 |
| 6. 전체 확정 | 5단계 | 가상조직, 해결과제 목록(번호, 해결과제명, 측정 역량) | "이대로 스토리맵을 쓸까요?" 승인 |
| 7. 스토리맵 | 6단계 | 형식 기준 스토리맵을 따른 스토리맵 + 역량-내용 연계 분석 표(내부 검토용, 제출본에서 뺄 수 있음) | 내용 확인, AI 수정 요청, [과제 초안으로 넘기기] |

- 단계마다 AI 수정 요청 상자(원칙 16)를 둔다.
- 근거 파일명을 누르면 서버에 있는 그 파일에서 RAG로 찾은 부분을 보여 준다(7-1).
- 고정한 해결과제명과 측정 역량은 프로젝트 이름 옆과 ② 이후 화면에도 계속 보인다.

|---|---|

| 나오는 것 | 블록 목록이 두 묶음으로 나온다. **평가과제**: 구조, 공통 자료, 역할별 자료. **평가자가이드**: 과제 개요, 역량별 행동 지표, 자료별 쟁점과 정답 근거, 평가자 질문, 채점 기준. 공통 편집 화면에서 연다. |
| 서로 연결 | 가이드의 "정답 근거"마다 과제의 어느 자료·쪽인지 연결해 둔다. 과제를 고치면 연결된 가이드 부분에 "함께 확인 필요"를 표시한다. |

### ③ 검토회의 보고서

화면은 3단계로 나눠 한 번에 하나씩 보여 준다: **1. 녹취록 확인 → 2. 양식 칸 확인 → 3. 미리보기·받기**

**3-1. 녹취록 만들기 (클로바노트와 같은 방식)**

| 순서 | 동작 |
|---|---|
| 1 | 음성 파일(mp3, m4a, wav)을 올린다. 참석 인원(3~5명)을 고른다. 모르면 "자동"으로 둔다. |
| 2 | 서버가 음성을 글로 바꾸고 화자를 나눈다. 결과는 `화자 1` ~ `화자 5`, 발언 시각, 발언 내용으로 나온다. |
| 3 | 화자 정보 고치기: `화자 1`을 누르고 이름("김○○"), 소속("○○대학교 교수"), 구분(검토위원 / 발주처 / 개발사)을 적으면 그 화자의 모든 발언에 한 번에 적용된다. 구분은 양식의 참석인원 칸과 "검토위원 의견", "발주처 의견", "개선 및 반영 방향" 열을 나눠 채우는 데 쓴다. 구분을 정하지 않은 화자가 있으면 칸을 채우기 전에 알려 준다. |
| 4 | 발언 줄을 누르면 그 시각부터 음성이 재생된다. 잘못 들린 글자를 그 자리에서 고칠 수 있다. |
| 5 | 화자가 잘못 나뉜 줄은 화자 이름을 눌러 다른 화자로 바꾼다. |

**3-2. 양식 채우기 (양식이 용역마다 달라도 됨)**

| 순서 | 동작 |
|---|---|
| 1 | 양식을 고른다. 같은 용역에서 쓴 적이 있으면 저장된 양식을 고르기만 한다. 없으면 hwpx 파일을 올린다. hwp 양식은 한글에서 "다른 이름으로 저장 → hwpx"로 한 번 바꿔 올린다(hwp를 올리면 이 방법을 안내한다). |
| 2 | AI가 양식을 읽고 채울 칸을 찾아 제안한다(아래 표). 이용자는 칸마다 [AI가 채움] / [비워 둠] / [직접 입력] 중 하나만 확인한다. |
| 3 | 이전 회차 내용이 들어 있는 양식을 올리면, 그 내용을 문체와 표기 방식의 예시로 쓴다. 예: 문장 끝 "~하겠음", 위치 표기 "[자료3. 제목(2/3), 6page]" |
| 4 | 평가과제 pptx(②나 ④의 파일)를 함께 고르면, 회의에서 "자료 3 두 번째 장"이라고 말한 것을 양식의 위치 표기 방식(자료 제목, 장 번호, 인쇄 쪽)으로 바꿔 적는다. |
| 5 | AI가 칸을 채운 미리보기를 보여 준다. 칸마다 근거가 된 발언으로 이동할 수 있다. 직접 고치거나 채팅으로 고친다. 예: "의견을 위원별로 나눠 줘" |
| 6 | [hwpx로 받기]. 확인한 칸 구성은 "발주처·용역명" 이름으로 저장되어 같은 용역의 2차, 3차 회의에 다시 쓴다. |

**샘플 양식에서 AI가 찾아야 할 칸 (제안 예시)**

| 양식의 칸 | 채우는 방법 |
|---|---|
| 제목줄(연도, 기관, 직급, 기법, 기수·차수) | 프로젝트 정보로 채움 |
| 건명, 일시 | 프로젝트 정보 + 녹음 파일 날짜로 채움 |
| 참석인원(총 n명, 구분별 소속·이름) | 3-1에서 고친 화자 정보로 채움 |
| 회의내용 표: 위치 행 | 의견이 가리키는 자료의 위치 표기. 첫 행은 "과제 전반" |
| 회의내용 표: "검토위원 의견" 열 | 검토위원 구분 화자의 발언을 요약 |
| 회의내용 표: "발주처 의견" 열 | 발주처 구분 화자의 발언 가운데 그 의견 행과 관련된 것을 찾아 요약. 관련 발주처 발언이 없는 행만 비운다. |
| 회의내용 표: "개선 및 반영 방향" 열 | 개발사 화자의 답변과 회의 결론을 "~하겠음" 문체로 요약 |
| 향후일정 표 | 회의에서 나온 다음 일정. 없으면 [직접 입력] |

- 회의내용 표는 "위치 행 1줄 + 내용 행 1줄"이 한 묶음으로 반복된다. AI는 이 반복 묶음을 찾아 의견 수만큼 복사한다.

**hwp 양식 처리 (방법 A로 확정)**
- 양식을 처음 등록할 때 이용자가 한글에서 "다른 이름으로 저장 → hwpx"로 바꿔 올린다. 양식은 용역별로 한 번만 등록하므로 한 번만 하면 된다.
- 결과는 hwpx로 내보낸다(한글 2014 이후 버전에서 열림).
- hwp 파일을 양식으로 올리면 거부하지 않고, 위 저장 방법을 화면에 안내한다.

### ④ 검토의견 반영

| 순서 | 동작 |
|---|---|
| 1 | 수정할 평가과제 pptx를 고른다. ②에서 만든 것이 있으면 자동으로 선택된다. 평가자가이드도 함께 불러온다. |
| 2 | **수정 요청 목록**은 ③ 보고서 표의 의견 행을 그대로 가져온다. 항목마다 위치, 검토위원 의견, 발주처 의견, 반영 방향, 근거 발언(시각)이 들어간다. ③을 거치지 않았다면 녹취록에서 새로 뽑는다. |
| 3 | 이용자가 반영할 항목에 체크한다. 서로 부딪치는 요청(예: 위원 A는 늘리자, 위원 B는 줄이자, 또는 위원과 발주처의 의견이 다름)은 따로 표시한다. |

| 5 | 공통 편집 화면의 검토 모드(5-6)에서 고친 안을 하나씩 [반영] / [다른 안 제안받기] / [넘기기]로 고른다. 바뀐 부분 보기로 확인한다. 과제를 고쳐 영향을 받는 가이드 부분에는 "함께 확인 필요"가 붙는다. |
| 6 | [pptx로 받기]. [반영 내역표 받기]를 누르면 "요청 → 반영 여부 → 고친 위치"를 표로 받는다. |
| 7 | [검토 교훈 남기기]를 누르면, 이번 의견 중 다른 과제에도 쓸 만한 교훈을 AI가 정리해 `isomorph-ac`의 `references/review-lessons.md`에 넣자는 제안을 관리자에게 보낸다(3-3 제안 대기). |

## 7. 관리자 화면

| 화면 | 하는 일 |
|---|---|
| 지침 관리 | 기능별 스킬 올리기 또는 지침 직접 쓰기, 스킬 파일 보기·직접 고치기·AI에게 고쳐 달라고 하기, 저장 전 규칙 점검, 이전·새 버전 시험 비교, 수정 기록, 제안 대기 (3-3~3-5) |
| 점검 항목 관리 | 점검 버튼 등록·수정·순서 변경, 점검 지침을 AI에게 고쳐 달라고 하기 (4장) |
| 자료·DB 관리 | 7-1 참고 |
| 양식·구조 관리 | 용역별로 저장된 보고서 양식(칸 구성)과 과제 파일 구조(자료 표기 방식, 묶음 규칙, 방향·쪽 크기) 보기·고치기·지우기 (5-4, 6장 ③) |
| 설정 | 웹 검색 켜기/끄기, 이용자 권한(이용자/관리자) |

- 관리자 화면으로 가는 버튼은 관리자 계정에만 보인다.

### 7-1. 자료·DB 관리

| 탭 | 들어 있는 것 | 쓰는 곳 |
|---|---|---|
| 기출 DB | 연도, 발주처, 직급, 기법, 해결과제명, 측정 역량, **서버 파일명** | ①의 드롭다운, 평가 조건 확인, 구조 분석, 중복 대조 |
| 발주처 주제풀 | 발주처, 직급, 연도, 주제, 선정 여부, 서버 파일명 | ① 중복 대조(배제 목록) |
| 실무 DB | 발주처, 연도, 부서, 담당 업무 | ① 무관 조건일 때 발주처 실무와 겹치는지 대조 |
| 역량 정의 | 기관, 직급, 역량, 하위요소 | ① 측정 역량과 하위요소 이름 |
| 참고 문서 | 평가과제, 평가자가이드, 기관 자료 파일 | ②④ 참고 검색 |
| 용역 설정 | 용역별 평가 조건, 구조 분석 결과, 확정 주제, DB 기준 정보(파일명, 행 수, 최근 연도, 서명) | ① 2·3단계 결과 재사용 |

- **드롭다운 연동**: ①의 발주처·직급 목록은 기출 DB와 주제풀에 있는 값으로 만든다. 행을 추가하면 목록에 바로 나타난다.
- **RAG 연결**: 표의 파일명은 사내 서버에 저장된 파일을 가리킨다. 포털은 파일명으로 서버 파일을 찾아 색인(검색용 조각)을 만들고, 화면에서 파일명을 누르면 찾은 부분과 파일 위치를 보여 준다. 파일이 서버에 없으면 표에 "파일 없음"을 표시한다.
- **관리 기능**: 행 추가·고치기·지우기(지울 때 한 번 더 묻기), CSV 가져오기·내보내기, [색인 다시 만들기]. 색인을 다시 만들면 DB 기준 정보가 바뀌고, 용역 설정 문서의 값과 다르면 ①에서 구조 분석을 다시 한다.

## 8. 서버 구성 요소 (사내 설치)

| 역할 | 후보 (오픈소스) | 비고 |
|---|---|---|
| 언어 모델 | 한국어 성능과 도구 호출을 지원하는 모델 | 긴 문서(과제 전체 + 가이드)를 넣으려면 128K 이상 입력 길이가 필요하다. |
| 음성 → 글 | Whisper 계열(large-v3 등) | GPU가 필요하다. 1시간 회의 기준 처리 시간을 시험으로 확인한다. |
| 화자 구분 | pyannote 계열 | 3~5명 회의 녹음으로 정확도를 미리 시험한다. |
| 참고자료 검색 (RAG) | 문서 임베딩 + 벡터 DB | 자료·DB의 파일명으로 서버 파일을 찾아 색인한다. 발주처·연도·기법·직급 정보로 거른다. |
| pptx 처리 | python-pptx | 가로·세로, 쪽 크기와 상관없이 읽고 쓸 수 있다. 그룹 도형과 차트 숫자까지 읽을 수 있다(샘플로 확인). |
| hwp 읽기 | olefile + 한글 5.0 형식 해석 코드 | 자료·DB 관리에 올린 hwp 문서를 검색용으로 읽는다(샘플 양식으로 확인). 양식 채우기에는 쓰지 않는다. |
| hwpx 쓰기 | hwpx 안의 XML 직접 처리 | hwpx는 zip 안의 XML 파일이라 칸 단위로 채울 수 있다. |
