# 역량평가 과제 개발 포털 기능 명세 (초안 v0.1)

- 작성일: 2026-11-10
- 상태: 검토 요청 중. 확인을 받은 뒤 이 명세에 맞춰 화면 시안(`ac-studio.html`)을 다시 만든다.
- 이전 시안과의 관계: 이전 시안의 3단계 흐름(역량 칩 선택 → 주제 후보 → 스토리맵·과제지·평정가이드 탭)은 폐기한다. 그 자리는 이 문서의 5개 기능 화면으로 바꾼다.

## 1. 전제 조건

| 항목 | 내용 | 상태 |
|---|---|---|
| 처리 위치 | 모든 처리(AI 모델, 음성 인식, 화자 구분, 파일 변환)는 사내 서버 안에서만 한다. 외부 AI API는 쓰지 않는다. | 확정 |
| 인터넷 | 웹 검색은 관리자가 켜고 끌 수 있게 만든다. 꺼져 있으면 사내 참고자료만 사용한다. | 사용 가능 여부 확인 중 |

## 2. 작업 원칙 (모든 화면에 공통 적용)

1. **화면에는 고를 것만 둔다.** 모델 선택, 프롬프트 작성, 온도·토큰 설정은 이용자 화면에 두지 않는다. 그런 설정은 관리자 화면에서만 다룬다.
2. **일정한 점검은 버튼으로, 그때그때 필요한 요청은 채팅으로 한다.** 매번 같은 기준으로 하는 점검은 관리자가 버튼으로 등록하고, 이용자는 누르기만 한다. 그 밖의 추가 점검이나 수정 요청은 채팅으로 받는다.
3. **AI가 지적하거나 고친 내용은 모두 문서 위 위치와 함께 보여 준다.** "어디가, 왜, 어떻게 고치면 되는지"를 한 묶음으로 보여 주고, 반영 여부는 이용자가 정한다.
4. **바뀐 내용은 언제든 되돌릴 수 있다.** AI가 고친 것이든 이용자가 고친 것이든 모두 버전으로 남기고, 이전 버전과 비교하거나 되돌릴 수 있다.
5. **숫자 계산은 프로그램이 한다.** AI는 "어느 숫자끼리 맞아야 하는지"만 찾는다. 합계, 비율, 날짜·요일 같은 계산은 서버의 계산 코드가 맡는다.
6. **지침은 한곳에서 관리한다.** 기능마다 쓰는 지침(스킬 또는 지침 프롬프트)과 점검 항목은 관리자 화면 한곳에서 고치고, 고친 내용은 모든 이용자에게 바로 적용된다.

## 3. 지침 관리 방식: 스킬 불러오기 + 지침 프롬프트

### 3-1. 기본 방식: 기존 스킬을 그대로 불러온다

기존 스킬 폴더(`SKILL.md` + `references/` + `scripts/`)를 관리자가 zip으로 올리면 포털이 다음처럼 나눠 쓴다.

| 스킬 구성 | 포털에서 쓰는 방법 |
|---|---|
| `SKILL.md` 본문 | 해당 기능의 지침 프롬프트(시스템 프롬프트)로 넣는다. |
| `references/` 문서 | 참고자료 저장소에 넣고, 지침이 그 문서를 언급할 때 찾아서 함께 넣는다. |
| `scripts/` 코드 | 서버의 격리된 실행 환경에서 돌린다. 예: pptx 읽기·쓰기, 표 계산 |
| `SKILL.md` 머리말(name, description) | 기능 선택 화면의 이름과 설명으로 쓴다. |

**미리 알아 둘 제약**
- 기존 스킬은 Claude가 웹 검색, 파일 생성, 코드 실행 도구를 쓴다고 가정하고 쓰여 있다. 오픈소스 모델에서 같은 결과를 내려면 포털이 같은 도구(웹 검색, 파일 읽기·쓰기, 코드 실행)를 모델에 제공해야 하고, 모델은 도구 호출(function calling)을 지원해야 한다.
- 도구를 제공하지 못하는 단계는 아래 3-2 방식으로 대신한다.

### 3-2. 대체 방식: 지침 프롬프트를 관리자가 직접 쓴다

스킬을 그대로 돌리기 어려운 기능, 또는 해당 스킬이 없는 기능은 관리자가 지침 프롬프트를 직접 입력한다.

### 3-3. 관리자 화면에서 지침을 다루는 규칙

- 기능마다 "스킬 불러오기" 또는 "지침 프롬프트 직접 쓰기" 중 하나를 고른다.
- 지침을 고칠 때마다 버전이 남는다(고친 사람, 날짜, 바뀐 줄). 이전 버전으로 되돌릴 수 있다.
- 저장하기 전에 예시 파일로 시험 실행을 해 볼 수 있다.

### 3-4. 기능별 지침 연결 (초안)

| 기능 | 연결할 지침 | 방식 |
|---|---|---|
| ① 주제 탐색 | `ac-topic-storymap` | 스킬 불러오기 |
| ② 과제 초안 | `isomorph-ac` | 스킬 불러오기 |
| ③ 검토회의 보고서 | (스킬 없음) 녹취록 요약·양식 칸 채우기 지침 | 지침 프롬프트 직접 쓰기 |
| ④ 검토의견 반영 | (스킬 없음) 수정 요청 뽑기·반영 지침. 필요하면 `isomorph-ac` 일부를 참조한다. | 지침 프롬프트 직접 쓰기 |
| ⑤ 검수 | 점검 항목(4장)을 그대로 사용 | 점검 버튼 |

## 4. 점검 항목 관리 (현실적합성, 오탈자 등)

### 4-1. 구조

관리자가 점검 항목을 등록하면, 이용자의 편집 화면 위쪽에 버튼으로 나타난다.

| 등록 칸 | 설명 | 예시 |
|---|---|---|
| 이름 | 버튼에 보일 이름 | 현실적합성 점검 |
| 지침 프롬프트 | 무엇을 어떤 기준으로 찾을지 적는다. | 실제 있는 법령·제도인가, 그 직급에 그 권한이 있는가, 예산·인원 규모가 현실적인가, 날짜와 요일이 맞는가 |
| 계산 코드 사용 | 숫자 계산이 필요한 항목이면 켠다. | 수치 점검에서 켬 |
| 표시 색 | 문서 위에 표시할 색 | 주황 |
| 보이는 기능 | 어느 단계 화면에 버튼을 보일지 정한다. | ②, ④, ⑤ |
| 순서·사용 여부 | 버튼 순서, 숨김 여부 | |

### 4-2. 처음에 넣어 둘 점검 항목 (관리자가 고치거나 지울 수 있음)

| 이름 | 찾는 것 | 계산 코드 |
|---|---|---|
| 현실적합성 | 실제와 맞지 않는 제도·권한·규모·일정 | 날짜·요일만 사용 |
| 오탈자 | 맞춤법, 띄어쓰기, 오타, 기관명·인물명 표기 불일치 | 사용 안 함 |
| 수치 계산 | 예산 합계, 비율, 증감률, 인원 합계가 맞는지 | 사용 |
| 자료 간 일치 | 같은 사실(금액, 날짜, 인물, 직위)이 자료마다 다르게 적혔는지 | 사용 |
| 근거 없는 내용 | 다른 자료에 근거가 없는 주장이나 결론 | 사용 안 함 |
| 표현 | 잘못된 용어, 응시자에게 정답을 알려 주는 표현, 차별적 표현 | 사용 안 함 |

### 4-3. 점검 결과를 보여 주는 방식

- 문서 위 해당 글자에 점검 항목 색으로 밑줄을 긋는다.
- 오른쪽에 결과 카드를 띄운다. 카드에는 **점검 항목 / 위치(예: 자료3, 2번째 표) / 문제 / 고친 안 / [반영] [무시]** 버튼이 들어간다.
- [반영]을 누르면 고친 안이 문서에 들어가고 새 버전이 남는다.
- 추가 점검이나 다른 수정은 채팅으로 요청한다. 예: "자료 2와 자료 5의 예산이 왜 다른지 다시 봐 줘"

## 5. 공통 편집 화면 (②, ④, ⑤가 같이 씀)

### 5-1. 배치

```
┌──────────────┬──────────────────────────────┬────────────────────┐
│ 블록 목록     │ 문서 본문                     │ 채팅 / 점검 결과    │
│  구조         │ [점검 버튼: 현실적합성 오탈자 …] │ 수정 범위: 자료 2   │
│  자료 1       │                              │ ─────────────────  │
│ ▶자료 2       │  (선택한 블록 내용)            │ 결과 카드 …         │
│  자료 3       │                              │                    │
│  …            │  [바뀐 부분 보기] [버전 기록]   │ [고칠 내용 입력]    │
└──────────────┴──────────────────────────────┴────────────────────┘
```

- 휴대폰 폭에서는 세 영역을 탭(목록 / 문서 / 채팅)으로 바꿔 보여 준다.

### 5-2. 수정 방법 3가지

| 방법 | 동작 | 채팅에 걸리는 범위 |
|---|---|---|
| 블록 클릭 | 왼쪽 목록에서 "자료 2"를 누른다. | 채팅창 위에 "수정 범위: 자료 2"가 표시되고, 요청은 자료 2에만 적용된다. |
| 드래그 선택 | 본문에서 글자를 드래그하면 작은 메뉴가 뜬다: [AI에게 고쳐 달라고 하기] [직접 고치기] | 드래그한 글자에만 적용된다. |
| 전체 요청 | 범위를 지정하지 않고 채팅에 쓴다. | 문서 전체. AI가 어느 블록을 고쳤는지 함께 알려 준다. |

### 5-3. 바뀐 부분 확인

- **바뀐 부분 보기**를 켜면 이전 버전과 비교해 지운 글자는 빨간 취소선, 넣은 글자는 초록 바탕으로 보인다.
- 왼쪽 블록 목록에서 바뀐 블록 옆에 점을 찍는다.
- **버전 기록**에는 버전마다 "누가(이용자/AI), 무엇 때문에(채팅 요청 문장, 점검 항목 이름), 어느 블록을" 고쳤는지 한 줄로 남는다. 아무 버전이나 골라 되돌릴 수 있다.

### 5-4. 파일 형식

- ②에서 만든 초안은 pptx로 내보낸다.
- ④와 ⑤는 pptx를 불러와 같은 편집 화면에 블록으로 보여 준다. 슬라이드는 제목을 기준으로 "자료 n"에 묶는다. 묶음이 틀리면 이용자가 끌어서 고친다.
- pptx를 고칠 때는 글자만 바꾸고 레이아웃, 글꼴, 표 모양은 그대로 둔다. 그림과 차트 안의 글자는 AI가 고치지 않고 "직접 고쳐야 할 곳"으로 표시한다.

## 6. 기능별 화면

### ① 주제 탐색

| 구분 | 내용 |
|---|---|
| 넣는 것 | 발주처, 직급, 평가 기법(서류함, 역할수행, 발표, 집단토론), 기출 DB와 주제풀 CSV(관리자가 미리 넣어 두면 고르기만 함), 원하는 방향(선택) |
| 처리 | `ac-topic-storymap` 지침 + 참고자료 저장소 검색 + 웹 검색(켜져 있을 때) |
| 화면 | 주제 후보 카드 3~5개. 카드마다 **비슷한 기출 과제**(제목, 연도, 겹치는 정도), **유불리·시의성 점검표**, 근거 출처 링크를 보여 준다. |
| 동작 | [이 주제로 스토리맵 만들기] / [다른 후보 보기] / 채팅으로 조건 추가(예: "환경 분야는 빼 줘") |
| 나오는 것 | 스토리맵. 공통 편집 화면에서 고칠 수 있다. [과제 초안으로 넘기기] 버튼이 있다. |

### ② 과제 초안

| 구분 | 내용 |
|---|---|
| 넣는 것 | 스토리맵(①에서 자동으로 넘어옴, 또는 파일 업로드), 참조할 평가과제(pptx/pdf), 평가자가이드(pptx/pdf/docx) |
| 처리 | `isomorph-ac` 지침 |
| 나오는 것 | 구조, 자료 1, 자료 2 … 블록으로 나뉜 과제 초안. 공통 편집 화면에서 연다. |
| 확인 필요 | 평가자가이드도 이 단계에서 함께 만들지 정해야 한다. 9장의 확인 필요 사항 1번을 본다. |

### ③ 검토회의 결과보고서

**3-1. 녹취록 만들기 (클로바노트와 같은 방식)**

| 순서 | 동작 |
|---|---|
| 1 | 음성 파일(mp3, m4a, wav)을 올린다. 참석 인원(3~5명)을 고른다. 모르면 "자동"으로 둔다. |
| 2 | 서버가 음성을 글로 바꾸고 화자를 나눈다. 결과는 `Speaker 1` ~ `Speaker 5`, 발언 시각, 발언 내용으로 나온다. |
| 3 | 화자 이름 바꾸기: `Speaker 1`을 누르고 "김○○ 위원"으로 바꾸면 그 화자의 모든 발언에 한 번에 적용된다. |
| 4 | 발언 줄을 누르면 그 시각부터 음성이 재생된다. 잘못 들린 글자를 그 자리에서 고칠 수 있다. |
| 5 | 화자가 잘못 나뉜 줄은 화자 이름을 눌러 다른 화자로 바꾼다. |

**3-2. hwpx 양식 채우기**

| 순서 | 동작 |
|---|---|
| 1 | hwpx 양식을 고른다. 관리자가 미리 등록한 양식이 있으면 고르기만 하고, 없으면 올린다. |
| 2 | 처음 쓰는 양식이면 칸 지정을 한 번 한다. 양식 미리보기에서 칸을 누르고 "회의 일시 / 참석자 / 주요 의견 / 수정 요청 / 결론"처럼 이름을 붙인다. 지정 내용은 저장되어 다음부터는 자동으로 적용된다. |
| 3 | AI가 녹취록을 바탕으로 칸별 내용을 채운 미리보기를 보여 준다. 칸마다 근거가 된 발언으로 이동할 수 있다. |
| 4 | 칸 내용을 직접 고치거나 채팅으로 고친다. 예: "주요 의견을 위원별로 나눠 줘" |
| 5 | [hwpx로 받기]. 이전 형식인 hwp는 받지 않는다(hwpx만 지원). |

### ④ 검토의견 반영

| 순서 | 동작 |
|---|---|
| 1 | 수정할 평가과제 pptx를 고른다. ②에서 만든 것이 있으면 자동으로 선택된다. 근거로는 ③의 녹취록이나 보고서를 고른다. |
| 2 | AI가 녹취록에서 **수정 요청 목록**을 뽑는다. 항목마다 요청 내용, 말한 사람, 발언 시각, 해당 블록(예: 자료 3)이 들어간다. |
| 3 | 이용자가 반영할 항목에 체크한다. 서로 부딪치는 요청(예: 위원 A는 늘리자, 위원 B는 줄이자)은 따로 표시한다. |
| 4 | AI가 체크된 항목별로 고친 안을 만든다. 이때 참고자료 저장소의 다른 평가과제와 평가자가이드를 찾아 근거로 붙인다. 예: "2024년 ○○과제 자료 4의 구성을 참고함" |
| 5 | 공통 편집 화면에서 고친 안을 하나씩 [반영] / [무시]한다. 바뀐 부분 보기로 확인한다. |
| 6 | [pptx로 받기]. [반영 내역표 받기]를 누르면 "요청 → 반영 여부 → 고친 위치"를 표로 받는다. |

### ⑤ 검수

| 구분 | 내용 |
|---|---|
| 넣는 것 | 완성된 평가과제 pptx(④ 결과가 있으면 자동 선택) |
| 화면 | 공통 편집 화면 + 점검 버튼 줄. [전체 점검]을 누르면 등록된 점검 항목을 모두 돌린다. |
| 결과 | 점검 항목별 개수 요약(예: 오탈자 7, 수치 계산 2, 자료 간 일치 1) + 문서 위 표시 + 결과 카드 |
| 동작 | 카드마다 [반영] / [무시]. 추가 점검은 채팅으로 한다. |
| 나오는 것 | 고친 pptx, 검수 결과표(엑셀) |

## 8. 서버 구성 요소 (사내 설치)

| 역할 | 후보 (오픈소스) | 비고 |
|---|---|---|
| 언어 모델 | 한국어 성능과 도구 호출을 지원하는 모델 | 긴 문서(과제 전체 + 가이드)를 넣으려면 128K 이상 입력 길이가 필요하다. |
| 음성 → 글 | Whisper 계열(large-v3 등) | GPU가 필요하다. 1시간 회의 기준 처리 시간을 시험으로 확인한다. |
| 화자 구분 | pyannote 계열 | 3~5명 회의 녹음으로 정확도를 미리 시험한다. |
| 참고자료 검색 | 문서 임베딩 + 벡터 DB | 발주처·연도·기법·직급 정보로 거르기 |
| 파일 처리 | pptx: python-pptx, hwpx: XML 직접 처리 | hwpx는 zip 안의 XML 파일이라 칸 단위로 채울 수 있다. |

## 9. 확인 필요 사항

1. **② 과제 초안에서 평가자가이드도 함께 만들까?** `isomorph-ac`는 가이드와 과제를 둘 다 만든다. 함께 만들면 ②의 블록 목록에 "가이드" 묶음이 추가된다.
2. **인터넷 사용 여부.** 현재 확인 중이다. 사용할 수 없으면 ①의 시의성 확인은 사내 자료로만 한다.
3. **검토회의 hwpx 양식 실물.** 양식을 받으면 칸 지정 예시를 실제 양식으로 만든다.
4. **pptx에서 "자료 n"을 나누는 기준.** 슬라이드 제목(예: "자료 3")으로 나누는 방식이 실제 과제 파일과 맞는지 샘플 1건으로 확인이 필요하다.
